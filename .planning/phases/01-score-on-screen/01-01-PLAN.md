## Facts pinned by planning-time probes (opensheetmusicdisplay@2.1.2, jsdom 29.1.1, Node v24.11.1, Chrome at C:\Program Files\Google\Chrome\Application\chrome.exe)

These were executed against the real bundle or read from the pinned 2.1.2 source during planning; write code to them, do not re-derive.

- OSMD `Fraction` values (`VoiceEntry.Timestamp`, `Note.Length`, `SourceMeasure.Duration`, `SourceMeasure.AbsoluteTimestamp`) are in whole-note units. Quarter-note beats = `GetExpandedNumerator() * 4` over `Denominator`, then reduce by gcd. MuseScore exports arrive unreduced (`12/8`, `4/8`); reduction is mandatory for stable ids.
- `note.halfTone` for middle C (MusicXML `<step>C</step><octave>4</octave>`) is `48`; MIDI note number = `halfTone + 12` (F#5 → 66 → 78, Eb3 → 39 → 51).
- `note.Pitch.ToStringShort(3)` returns scientific names with the written accidental: `C4`, `F#5`, `Eb3`. The `3` equals `opensheetmusicdisplay.Pitch.OctaveXmlDifference`.
- `staffEntry.ParentStaff.Id` is the MusicXML `<staff>` value (1 or 2) and defaults to 1 when the element is absent. `voiceEntry.ParentVoice.VoiceId` is the literal MusicXML `<voice>` value (MuseScore uses 1 for staff 1 and 5 for staff 2).
- `measure.MeasureNumberXML` is the literal `<measure number="">` attribute. `measure.ActiveTimeSignature.Numerator/Denominator` hold beats/beat-type unreduced (`4/4`, `3/4`, `5/4`).
- A chord is one `VoiceEntry` with several `Notes` in document order. Rests are `Note` objects with `isRest() === true`. A tie is `note.NoteTie` (one `Tie` object shared by every note of the chain, with `Notes[]` and `StartNote`); the start note satisfies `note.NoteTie.StartNote === note`. OSMD's reader joins a middle note carrying both `<tied type="stop"/>` and `<tied type="start"/>` into the same `Tie` (its two-element branch), so a three-segment chain is one `Tie` with three `Notes`. The `TieTypes` enum is unrelated (guitar articulation) and must not be consulted.
- The UMD bundle at `https://cdn.jsdelivr.net/npm/opensheetmusicdisplay@2.1.2/build/opensheetmusicdisplay.min.js` assigns `window.opensheetmusicdisplay` when loaded by a classic script tag; it exports `OpenSheetMusicDisplay`, `Fraction`, `Pitch`. Under Node the same file is `require("opensheetmusicdisplay/build/opensheetmusicdisplay.min.js")`.
- `osmd.load(content)` accepts a UTF-8 string, a `Blob`, or a `File` (read via `readAsArrayBuffer`, binary-safe, `.mxl` detected internally). `render()` under jsdom throws `HTMLCanvasElement's getContext()` — tests must never call `render()`; `load()` alone populates `osmd.Sheet`.
- **Notehead addressing (review finding 1, read from the pinned 2.1.2 source `VexFlowGraphicalNote.ts`, `VexFlowConverter.ts`, `GraphicalVoiceEntry.ts` and the bundled VexFlow 1.2.93):** `osmd.EngravingRules.GNote(note)` returns the `VexFlowGraphicalNote`. Its `getSVGGElement()` returns the VexFlow stave-note group (`<g class="vf-stavenote" id="vf-...">`) shared by every note of a chord, so it is NOT a per-pitch handle and must not be used as the map value. VexFlow 1.2.93 draws each notehead as `<g class="vf-notehead">` (no id, no `el` attribute) inside the `<g class="vf-note">` child of that group, in `note_heads` order. Before building the stave note OSMD calls `gve.sortForVexflow()` (ascending `halfTone`) and then `setIndex(vfnote, i)` for `notes[i]`, so `gNote.vfnoteIndex` is the note's position in `note_heads`, and `gNote.getNoteheadSVGs()` (2.1.2 public method) returns exactly the `vf-notehead` children of the `vf-note` group in that same order. Therefore the per-pitch notehead is `gNote.getNoteheadSVGs()[gNote.vfnoteIndex]`. `gNote.getSVGId()` returns the VexFlow id (for example `auto482`) of the stave-note group — useful as a chord fingerprint. All of these only return elements after a real `render()` in a browser (null/empty under jsdom) and are replaced on every re-render.
- **Node 24 globals (review finding 2, verified on this machine):** `Object.getOwnPropertyDescriptor(globalThis, 'navigator')` is `{ get: function, set: undefined, configurable: true }`; a plain assignment in sloppy mode silently leaves the original in place and in strict mode throws; `Object.defineProperty(globalThis, 'navigator', { value, configurable: true, writable: true })` succeeds. `File` and `Blob` already exist on `globalThis` as writable data properties; `window`, `document`, `FileReader`, `DOMParser` are absent.
- **Headless Chrome (not probed at planning time; design facts only):** Chrome is installed at `C:\Program Files\Google\Chrome\Application\chrome.exe`. Launching it without `--user-data-dir` attaches to the user's running Chrome (observed: "Opening in existing browser session."), so a developer check must always pass a fresh `--user-data-dir`. `--headless=new --remote-debugging-port=0` prints `DevTools listening on ws://127.0.0.1:<port>/devtools/browser/...` on stderr; `http://127.0.0.1:<port>/json/list` lists targets with `webSocketDebuggerUrl`; `Runtime.evaluate` with `returnByValue: true` returns `{ id, result: { result: { value } } }`. Node 24 has a global `WebSocket` and `fetch`. `--allow-file-access-from-files` lets an `XMLHttpRequest` from a `file://` page read a sibling `file://` URL (`fetch()` rejects the file scheme regardless, so the dev hook uses XHR).
